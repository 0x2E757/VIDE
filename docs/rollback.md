# Rollback

All instance state is derived from the system (systemd units + `/etc/vide/*.env`
+ per-user `config.yaml`), never from the repo. A reverted tree therefore
re-converges cleanly: no password rotates and no session drops.

What a converge *does* re-assert, deliberately, and a revert takes back with it:
the `code-server@` template unit, `units/code-server-launch`,
`units/oauth2-proxy.service`, `units/oauth2-proxy.socket`, and the generated
`proxy.toml`. The units and `proxy.toml` are byte-compared, so an unchanged tree
rewrites nothing. None restarts the shared proxy: a converge run for one user
must not be able to drop the auth gate for everyone else, so a changed unit or
config is reported and applied by `sudo vide upgrade-sso` when you choose.
Secrets are never regenerated by a converge — `proxy.env`'s cookie secret is
preserved even when the client credentials are re-affirmed.

## Rolling back a change

```bash
git log --oneline        # find the commit that introduced the problem
git revert <commit>
sudo ./install.sh        # re-converge onto the reverted tree
vide doctor              # green = the box matches the tree again
```

`/usr/local/bin/vide` is a symlink to `<repo>/vide` in the checkout you ran
`install.sh` from, so a flip between two trees needs no cleanup. The corollary:
the box's `vide` command is only as durable as that checkout. If you roll back by
cloning somewhere else, or delete the old tree, `vide` dangles until you re-run
`install.sh` from the new location. Reverting **in place**, as above, never hits
this.

`git revert` undoes code, not system state. If the reverted commit had
already provisioned something new on the box (a unit, a file under
`/etc/vide`), the revert does not remove it — check the commit's diff for
provisioning steps and undo those with the pre-revert tree's own verbs
(`vide down` / `vide destroy`) before re-converging.

## Backing out a unit-template change

A revert re-asserts the unit **files**, and that is all it does. Both templates
govern the NEXT process, not the running one, so on a live box the backout has a
second half you have to run yourself.

### The instance template (`units/code-server@.service`)

```bash
git revert <commit> && sudo ./install.sh     # lands the file
sudo systemctl restart code-server@<user>    # one instance at a time
```

Restart the instances **one at a time**, and check `vide status <user>` between
them: under SSO the template's `ExecStartPost=` is what grants `caddy` access to
the instance socket, so a template that cannot run leaves that instance
unreachable, and doing all of them at once turns one bad revert into a fleet-wide
outage instead of a single failure you can stop at.

There is **no safe emergency drop-in** for this unit. Clearing `ExecStartPost=`
with an override looks like the obvious way to disarm a misbehaving template, and
it is wrong: the whole `vide-proxy` grant lives in that one line, so an instance
started with it cleared comes up healthy, reports active, and is unreachable
through Caddy. If a template genuinely will not start, revert the file and
restart — do not override it.

### The reservation socket (`units/oauth2-proxy.socket`)

This one has an ordering rule that a plain revert does not know about. The socket
unit holds `127.0.0.1:<proxy port>` as PID 1; `proxy.toml` tells the proxy to
inherit that descriptor with `http_address = "fd:3"`. **The two must move
together, and the toml must never name `fd:3` while the socket unit is absent** —
a box in that state serves normally and then fails to start its authorization
gate at the next reboot, unattended.

**The reservation has to be released before the reverted proxy is asked to
bind.** A revert makes `proxy.toml` name `127.0.0.1:<port>` again, but it does
not touch the socket unit already installed on the box — the reverted tree does
not know that unit exists. Restart the service in that state and the proxy tries
to bind a port PID 1 is holding, gets `EADDRINUSE`, and — with `Restart=always`
and no start limiter, both of which the revert also has not removed from the
running manager's view until it is reloaded — crash-loops **without ever landing
in `failed`**, which is the one state an operator watches for. So:

```bash
# 1. release the address FIRST — everything else fails EADDRINUSE until you do
sudo systemctl stop vide-oauth2-proxy.socket        # stops the service with it
sudo systemctl disable vide-oauth2-proxy.socket
sudo rm -f /etc/systemd/system/vide-oauth2-proxy.socket
sudo systemctl daemon-reload

# 2. now land the reverted tree, which rewrites proxy.toml back to an address
git revert <commit>
sudo ./install.sh

# 3. and start the gate on it
sudo systemctl reset-failed vide-oauth2-proxy.service
sudo systemctl start vide-oauth2-proxy.service
vide doctor
```

Note what step 1 costs, because it is precisely the thing being backed out: from
that moment nothing reserves the fleet's authorization port, and any local
account can bind it whenever the proxy is not holding it. Between steps 1 and 3
the window is wide open. Keep it short, and do not walk away in the middle.

If you are reverting to a tree that still *has* the socket unit — an ordinary
revert of some later commit — skip step 1 entirely and use the normal lever:

```bash
git revert <commit> && sudo ./install.sh
sudo vide upgrade-sso                    # restarts the gate; the socket keeps the port
vide doctor                              # the reservation rows must agree
```

`systemctl restart vide-oauth2-proxy.socket` is **not** a diagnostic step here.
`Requires=` propagates, so restarting the socket restarts the gate for the whole
fleet; and a `stop` frees the address. Start it, never bounce it.

## Rolling back an SSO-mode instance

Mode is immutable — there is no in-place SSO→password switch. The rollback
is destroy + password-mode reinstall:

```bash
sudo vide destroy <user>          # removes code-server/config/port record; keeps $HOME
sudo ./install.sh --no-gui --user <user> [--fqdn <name>]   # fresh password-mode instance
```

Destructive by design: a new code-server password is generated and shown
once. The user's `$HOME` — and everything in it — survives.

## What rollback does not cover

There is no route back to an earlier *implementation*, only to an earlier commit
of this one. Every promise above is about reverting code while the box keeps its
state. `tests/host-smoke/rollback.sh` covers those three promises and nothing
beyond them — and less than all of one: it deliberately does not assert the "no
session drops" half under SSO, and says so at the top of the file.

**The two unit-template sections above are not among them.** That tier reverts a
tree and re-converges; it does not restart an instance to land a template change,
and it has never backed a socket unit out of a running fleet. Both sequences are
written from how the units behave, not from a run that proved them — so treat
them as instructions to follow carefully on a box you can afford to break, and
read `vide doctor` after each step rather than at the end. Closing that gap needs
`tests/host-smoke/rollback.sh` extended and executed on a disposable box.
